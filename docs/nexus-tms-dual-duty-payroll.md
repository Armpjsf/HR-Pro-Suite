# พนักงานงานคลังที่รับค่าเที่ยวจาก Nexus TMS

ใช้รหัสพนักงาน HR คนเดิม เงินเดือน ตำแหน่ง แผนก และการลงเวลาไม่เปลี่ยน ค่าเที่ยวเป็นรายได้เพิ่มเติมใน `driving_pay` แยกจากโบนัสและเงินคืนค่าใช้จ่าย แสดงในหน้าระบบ สลิปพนักงาน สลิปพิมพ์ และรวมในยอดเงินได้ของเอกสารภาษี

## ติดตั้ง

1. ฝั่ง HR ต้องมี schema หลักถึง `schema-phase21.sql` และ migration ที่มีอยู่ก่อนหน้าใน `supabase/migrations/001..009` แล้วรัน `010_driving_income.sql` ผ่าน migration runner/transaction ของระบบ
2. ฝั่ง **nexus-tms-core** รัน `supabase/migrations/202611180001_driver_earning_lines.sql` และ deploy API v2 ทั้งอ่านรายเที่ยวและจองการจ่าย
3. ตั้งค่าฝั่ง HR บนเซิร์ฟเวอร์เท่านั้น:

   ```env
   HR_TENANT_ID=<บริษัทเดียวกับ TMS>
   NEXUS_TMS_URL=https://<โดเมน nexus-tms-core>
   NEXUS_TMS_API_KEY=<key ที่ผูกบริษัท/connection/สาขา>
   NEXUS_TMS_CONNECTION_ID=<connection_id ของ key>
   ```

4. API key ฝั่ง TMS ต้อง active, ไม่หมดอายุ, มี `tenant_id`, `connection_id`, `allowed_branches` และสิทธิ์ `earnings:read`, `earnings:claim` เปิดโมดูล HR/TMS และสถานะที่อนุญาต integration ใน entitlement ด้วย
5. ไม่มีการย้ายโบนัสเก่าเป็นค่าเที่ยวอัตโนมัติ หากมีชุด TMS ที่ลงสลิปด้วยโครงสร้างเดิม migration จะหยุดให้ตรวจแยกยอดก่อน เพื่อรักษาประวัติการจ่าย

ไฟล์ SQL ที่เพิ่มยังต้องนำไปรันในฐานข้อมูลจริง และต้องตั้งค่า URL/key จริงก่อนเปิดใช้ การทดสอบพัฒนาใช้ฐานข้อมูลแยกและ TMS จำลองเท่านั้น

## ขั้นตอน HR

1. ไปที่ **เงินเดือน → ค่าเที่ยวจาก Nexus TMS** เลือกงวด แล้วกด **ดึงรายเที่ยวเพื่อตรวจสอบ**
2. จับคู่รหัสคนขับกับรหัสพนักงานที่ยังทำงานอยู่ ยืนยันตามตัวบุคคลจริง ไม่จับคู่จากชื่ออัตโนมัติ วันที่มีผลเริ่มต้นเป็นวันแรกของงวดที่เลือก
3. กด **สร้างชุดนำเข้าเพื่อตรวจยอด** ตรวจเลขงาน รุ่นข้อมูล ยอดแต่ละเที่ยว และยอดพัก/ยอดที่ข้าม
4. กด **ยืนยันตรวจยอดแล้ว → อนุมัติค่าเที่ยว → ลงค่าเที่ยวในสลิป** แยกเป็นแต่ละขั้น ระบบบันทึกผู้ดำเนินการ แต่ไม่ได้บังคับว่าต้องเป็นคนละผู้ใช้
5. กด **คำนวณเงินเดือนใหม่** เพื่อนำเงินเดือน OT โบนัส ค่าเที่ยว ค่าใช้จ่าย และรายการหักมาคำนวณร่วมกัน ตรวจภาษีและยอดสุทธิก่อนกดยืนยันจ่ายตามขั้นตอนปกติ

นำเข้าหรือกลับรายการแล้วจะตั้ง `recalculation_required=true` ฐานข้อมูลปฏิเสธการยืนยันจ่ายจนกว่าจะคำนวณใหม่ การแก้สลิปด้วยมือไม่ปลดสถานะนี้และแก้ค่าเที่ยวโดยตรงไม่ได้

## หลักการรับค่าเที่ยวและป้องกันจ่ายซ้ำ

- นับงวดตาม `Verified_At` ในเวลาไทย ต้องมีหลักฐานวันที่ตรวจรับ ไม่ดึงเพียงงานที่ส่งสำเร็จแต่ยังไม่ตรวจรับ
- รายได้ต่อเที่ยวคือ `Cost_Driver_Total + Cost_Driver_Extra` ของงาน ใช้เลขงานสร้างรหัสรายได้ถาวรและใช้รุ่นข้อมูลประกอบ ไม่รวมจากชื่อคนขับ
- รายการที่มี `Driver_Payment_ID` จะถูกตัดออก แม้ใบจ่ายใน TMS ยังไม่ชำระ เพื่อไม่ให้จองช่องทางจ่ายซ้อนกัน
- ผู้รับเหมาช่วงถูกแยกออก พนักงานที่ไม่ active หรือยังไม่จับคู่จะพักรายการ ยอดพักไม่ได้ลงสลิป
- ก่อนลงสลิป HR อ่านแหล่งข้อมูลใหม่และให้ TMS จองงานแบบ transaction ตรวจรหัสคนขับ รุ่น ยอด สาขา และการจัดจ่ายเดิม หากผิดแม้แต่รายการเดียวจะไม่จองทั้งชุด
- งานที่จองให้ HR แล้วจะไม่สามารถผูกใบจ่ายคนขับ TMS หรือเปลี่ยน/ล้างผู้จองได้อีก แม้ HR ลงสลิปล้มเหลวหรือกลับรายการ ต้องดำเนินการจ่ายต่อผ่าน HR เท่านั้น การลองลงสลิปซ้ำใช้การจองเดิมได้
- รายได้รุ่นเดิมนำเข้าซ้ำไม่ได้ รุ่นใหม่ใช้เฉพาะส่วนต่างเมื่อรุ่นก่อนลงสลิปแล้วในงวดเปิดและพนักงานคนเดิม ฐานข้อมูลตรวจส่วนต่างอีกครั้งภายใต้ lock
- ถ้ารุ่นเดิมยังรออนุมัติ มีรุ่นใหม่กว่า เปลี่ยนพนักงาน เปลี่ยนงวด หรืองวดเดิมปิดแล้ว ให้พักตรวจและจัดทำรายการปรับปรุงที่มีผู้อนุมัติ ไม่โอนยอดข้ามคนหรือข้ามงวดอัตโนมัติ
- ยกเลิกชุดที่ยังไม่จ่ายพร้อมเหตุผลได้ ต้องกลับรุ่นใหม่ก่อนรุ่นเก่า สลิปที่จ่ายแล้วแก้หรือกลับรายการไม่ได้ งานที่ยกเลิกใน TMS และเคยตรวจรับจะส่งยอดศูนย์ในรุ่นใหม่เพื่อให้ตรวจส่วนต่าง

## การตรวจรับก่อนเปิดใช้จริง

ใช้พนักงานทดสอบที่มีงานคลังและขับรถ ยืนยันว่าเงินเดือนและแผนกคงเดิม ค่าเที่ยวเป็นอีกบรรทัด โบนัสยังเป็นยอดเดิม และยอดสุทธิ/ภาษีตรงกับการตรวจของ HR ทดลองดึงซ้ำ รุ่นแก้ไข งานที่จัดจ่ายใน TMS ผู้รับเหมาช่วง คนที่ยังไม่จับคู่ และการกลับรายการ ใช้ staging เท่านั้นก่อนทดสอบธุรกรรมจริง

ชุดทดสอบที่เกี่ยวข้อง: `tests/dual-duty-payroll.test.mjs`, `tests/phase-e-f-integrations-and-flows.test.mjs`, `tests/codex-r01-r03-db-durability.test.mjs` และ `nexus-tms-core/src/lib/__tests__/driver-earning-lines.test.ts`

ผลตรวจในเครื่องวันที่ 18 พฤศจิกายน 2026: HR `npm test` ผ่าน 54 รายการ, production build ผ่าน, lint ไม่มี error (มีคำเตือนรูปภาพเดิม 15 รายการ) ฝั่ง TMS `npm run typecheck` ผ่าน และ `npx vitest run --maxWorkers=2 --testTimeout=15000` ผ่าน 38 รายการ

`tests/ui/tms-payroll.browser.mjs` ทดสอบหน้า production บน Edge headless ด้วย API จำลองทั้งหมด ผ่านการจับคู่ ตรวจยอด อนุมัติ ลงสลิป คำนวณใหม่ การเชื่อมต่อล้มเหลว การลองใหม่ และงวดไม่มีรายการ ตรวจหน้าจอ 1440 และ 390 พิกเซล สามารถตั้ง `PLAYWRIGHT_MODULE` เป็น file URL ของ Playwright ที่ติดตั้งภายนอกโปรเจกต์ แล้วรันขณะเปิด HR ที่ `localhost:3137` จึงไม่จำเป็นต้องเพิ่ม dependency เพื่อใช้แอปจริง

ชุดเผยแพร่ที่แยกจากงานพัฒนาอื่น: ทดสอบ HR 35 รายการผ่าน รวม API นำเข้าและจ่ายจริงในฐานข้อมูลทดสอบ พร้อม production build และ browser workflow ที่ใช้ API จำลอง ฝั่ง TMS มี unit test เฉพาะ API รายเที่ยวและการตรวจ key 6 รายการผ่าน และ TypeScript ผ่าน
